Heurist Record Query Language

The Heurist record query language filters records by record header values, detail fields, links, relationships, geographic extent and user data. A query may be written as compact plain text or as JSON. Plain text is convenient for interactive searches; JSON is recommended for applications, nested paths and logical expressions.

Quick start

The following examples use Person record type 10, Place type 12, Event type 48, and example detail type IDs.

QueryMeaning
JohnsonRecords whose title contains “Johnson”.
t:10All Person records.
t:PersonAll Person records, resolving the singular record-type name before searching.
t:10 title:JohnsonPerson records with “Johnson” in the title.
t:10 f1:JohnsonPersons whose field 1 contains “Johnson”.
t:Person fGender:malePersons whose Gender field contains the term whose label or code is “male”.
t:10 sortby:titlePersons sorted by title.
{"t":10,"f:20":414}Persons with term 414 in field 20.
{"t":10,"lt:134":{"t":12,"title":"Baghdad"}}Persons linked through field 134 to a Place titled Baghdad.

The query is supplied in the q or query request parameter. The parameters limit, offset, fields, detail and rules are request options; they are not query predicates.

Plain-text format

Plain-text queries consist of predicates separated by spaces. A predicate can use keyword:value or keyword value. Conditions at the same level are combined with AND.

t:10 title:Johnson
t 10 f1 Johnson
t:10 title:"Johnson, John" sortby:title

A word without a recognised keyword is a title search. Quote values containing spaces. A leading - negates a word or a value:

t:10 -Smith
t:10 title:-Smith

Basic linked subqueries can be written with parentheses:

t:10 linkedto(t:12 title:Baghdad)
t:10 lt240(t:48 lt134(t:12 title:Berlin))

Although basic parenthesised links are accepted, use JSON for complex nested links, relationship constraints, repeated predicates, or logical combinations. Plain text is intended primarily for direct user input.

Name and value resolution

Names and semantic values are resolved to local numeric IDs before the main record query is composed and executed by the SQL server. The resolved query therefore uses the same indexed predicates as a query written with IDs.

InputResolution
t:Person or t:PersonsMatches a record type by its singular rty_Name or plural rty_Plural. Exact matches are preferred; otherwise a unique partial match is accepted.
fGender:maleResolves the unspaced field name and then resolves an enum label or code. This is equivalent to using the local field and term IDs.
{"t":"Events","f:Date of event":"yesterday"}JSON permits field names containing spaces.
usr:brandonResolves a login name to the user ID before searching bookmarks. Login names are also accepted by ws, owner and addedby.
{"f:20":"-male"}Resolves an enum label or code while preserving the negation operator.
{"sortby":"f:Population"}Resolves a named field before applying typed field sorting.

When a query level specifies one or more record types, field-name lookup is restricted to fields belonging to those types through defRecStructure. Each nested linked query has its own record-type context. Without a type predicate, field names are matched against all record structures.

If a partial record-type or field name has several matches, the query is rejected and the error lists the matching IDs and names. If a type-scoped field is not present in that record type, the query is rejected rather than silently searching for a similarly named global field.

JSON format

A simple query can be a JSON object. Multiple values of the same predicate, or an explicit ordered sequence of predicates, should use an array of one-key objects:

{"t":10,"title":"Johnson"}

[
  {"t":10},
  {"f:240":"-NULL"},
  {"sortby":"title"}
]

Do not repeat the same key within a JSON object because JSON object keys must be unique. Use the array form instead.

Numeric ranges

{"f:1160":"4000000<>5000000"}
{"f:1160":"<>4000000/5000000"}
{"f:1160":"><4000000/5000000"}

low<>high and the leading forms select scalar numeric values that fall within the supplied interval. The leading <> and >< forms also accept slash, comma, or “to” as the interval separator.

Date and temporal values

Simple dates use ISO forms such as 2025, 2025-01 and 2025-01-10. Heurist temporal JSON values stored in date fields are searched through their estimated minimum and maximum bounds.

Relative expressions are converted to absolute ISO dates before temporal bounds are calculated. A bare month or year denotes a complete period; month ago and year ago denote a single relative date.

Fulltext search

Fulltext operators use the MySQL/MariaDB fulltext indexes. For an unsuffixed f predicate, Heurist searches ordinary searchable details and linked-record titles. Enum labels/codes are also considered.

Plain textJSONMeaning
f:"@Johnson Berlin"{"f":"@Johnson Berlin"}Records matching any indexed word.
f:"@+Johnson John"{"f":"@+Johnson John"}All significant words must match within a searchable indexed value or linked title.
f:"@-Johnson"{"f":"@-Johnson"}Exclude records found by the positive fulltext search.
f1:"@Johnson"{"f:1":"@Johnson"}Fulltext search restricted to field 1.
f:"@Johnson -Berlin"{"f":"@Johnson -Berlin"}Explicit + or - word modifiers select Boolean mode.

For @+ and @-, Heurist removes established stop words and words shorter than 3 bytes or longer than 84 bytes before issuing the indexed search. With @+, every remaining word is marked as required in Boolean mode. With @-, Heurist first finds the complete positive candidate set and then excludes those records.

If an @+ or @- expression contains no indexable words after normalization, Heurist falls back to a substring LIKE condition. This allows searches containing only short, overlong or stop-listed words to retain useful semantics. Fulltext matching is nevertheless not generally equivalent to substring matching.

Complex JSON queries

Nested resource links

lt follows a resource field from the current record to its target. lf follows it in reverse. Omitting the field ID searches all ordinary resource fields.

{
  "t": 10,
  "lt:240": {
    "t": 48,
    "f:237": 6304,
    "lt:134": {
      "t": 12,
      "f:133": 10443
    }
  }
}

This finds Persons linked through field 240 to Events of type 6304, where the Event links through field 134 to Places classified by term 10443.

A direct linked ID can be supplied without a subquery:

{"t":10,"lt:134":51}

Existence: any linked record, or none

A link or relationship condition already means "at least one such linked record exists". An empty value matches any linked record:

{"t":10,"lt:240":[]}

To find records without such a link, add "exists":"NULL" inside the value. It works for lt, lf, links, rt, rf, related and connected:

{"t":4,"related:245":[{"t":10},{"exists":"NULL"}]}

This finds Organizations with no Person related through field 245.

"exists":"-NULL" (or an empty value) is the default and can be omitted.

Relationship queries

A relationship is a Relationship record connecting a source record and a target record with a relationship type (a term). It is stored once, from the record on which it was entered, so the same connection may be stored in either direction.

PredicateDirectionRelationship type
rt[:FIELD]Strict: the current record is the stored source.The stored type is in r / the field's vocabulary.
rf[:FIELD]Strict: the current record is the stored target.The stored type is in r / the field's vocabulary.
related[:FIELD]Either stored direction.The stored type or its inverse is in r / the field's vocabulary.

The optional FIELD suffix is always a relationship (relmarker) field ID or name, never a relationship type. The field supplies:

  • its vocabulary, which limits the relationship types (child terms included);
  • its record types: the record types that have the field (owner) and the field's target record types. For rt the current record must be of an owner type and the related record of a target type; for rf the other way round; for related either pairing. A t inside the value narrows this further.

Conditions on the Relationship record itself go inside the value:

  • r: the stored relationship type (term ID or comma list, child terms included). With related the term or its inverse matches, so either end of the relationship is found;
  • relf:FIELD (short form r:FIELD): a field of the Relationship record, for example its start date.
{
  "t": 4,
  "related:245": [
    {"t": 10},
    {"r": 5419},
    {"relf:10": ">2001"}
  ]
}

This finds Organizations related, in either direction and through the vocabulary of field 245 (Organization to Person), to Persons with relationship type 5419 and a relationship start date after 2001.

{
  "t": 4,
  "rt:245": {
    "t": 10
  }
}

This finds Organizations that are the stored source of a field-245 relationship to a Person. Use related when it does not matter on which record the relationship was entered.

Without a suffix and without r, related finds records with any relationship to the given records (here 100, 200 or 123):

{"t":10,"related":{"ids":"100,200,123"}}

Link paths used for linked output fields, map and timeline fields use the same prefixes followed by a field ID, with r for related: for example 10:r245:4:1 (Person, related through field 245 to Organization, its field 1).

Logical groups: all, any and not

Conditions in a normal object or array are combined with AND. Logical groups can be nested at any query level:

{
  "t": 10,
  "any": [
    {"lt:134": {"ids": 51}},
    {"ids": 152}
  ]
}
{
  "t": 10,
  "not": [
    {"lt:240": {"f:237": 6305}}
  ]
}
GroupMeaning
allEvery contained condition must match.
anyAt least one contained condition must match.
notExclude records matching the contained conditions.

Terms, tags and language values

Enum and relationship-type fields accept local term IDs. For enum fields, an exact term label or code is resolved to its local ID before the main query. Resolution is restricted to the field’s configured vocabulary and, when present, its record-type-specific filtered term tree. Descendant terms are included unless exact matching is requested with =. A label, code or concept ID can also be selected explicitly in JSON by extending the field key:

{"f:133":10443}
{"f:133":"Administrative.Capital"}
{"f:133":"capital"}
{"f:133":"=10443"}
{"f:133:label":"Administrative.Capital"}
{"f:133:code":"capital"}
{"f:133:concept":"2-10443"}

Translated freetext and term labels can use a two- or three-letter language prefix, or all::

{"f:1":"eng:London"}
{"f:133:label":"fre:Capitale"}
{"f:133:label":"all:Capital"}

Tags support one tag, any of several tags, all tags, presence and absence:

{"tag":"key1"}
{"tag":{"any":[1,2]}}
{"tag":{"all":[1,2]}}
{"tag":"NULL"}
{"tag":"-NULL"}

Spatial and viewport search

A viewport is expressed in JSON using longitude/latitude bounds:

{
  "geo": {
    "west": -16,
    "south": 32,
    "east": 40,
    "north": 72
  }
}

The viewport uses spatial intersection. Longitude must be between −180 and 180, latitude between −90 and 90, and south must not exceed north. A WKT geometry value uses containment:

{"geo":"POLYGON((-16 32,40 32,40 72,-16 72,-16 32))"}

Use geo:FIELD to restrict the search to one geographic detail field.

Sorting

A leading - means descending and + means ascending. Multiple sort expressions can be supplied as a comma-separated value or JSON array.

{"sortby":"-modified,title"}
{"sortby":["f:1160","title"]}
{"t":"Places","sortby":"-f:Population"}

Filtering, pagination and expansion rules

The Records endpoint accepts the following principal request parameters:

ParameterMeaning
q, queryPlain-text or JSON record filter.
idsRequest alias for q=ids:<CSV>.
limitMaximum records returned in the current page.
offsetZero-based result offset.
fieldsFields requested from the later output/details stage.
detailRequested output detail level.
rulesExpansion rules applied after the main result set. Historic name for expansion.

Filtering and expansion are different operations. A nested link in q filters the top-level result. rules starts with that result and retrieves linked records for maps, attributes, graph data or other output. Expanded records do not provide reliable top-level pagination and count semantics.

An expansion path may be written as an established JSON ruleset or as a compact path such as:

10:lt240:48:lt134:12

The compact path is converted to the corresponding JSON ruleset before execution.

Common errors and limitations

  • Record types may use local IDs, singular names or plural names. Fields may use local IDs or names; enum values may use local term IDs, labels or codes.
  • In plain text a field name containing spaces is quoted: f:"Date of birth"<1900; unspaced names may also be written fGender:male.
  • Ambiguous partial record-type or field names are rejected and the error lists the matches.
  • Do not repeat a key inside one JSON object; use an array of one-key predicates.
  • Use JSON for complex nesting and logical groups.
  • usr:current, ws:current, rating sort and other current-user operations require authentication.
  • The suffix of rt, rf and related (for example related:245) is a relationship field ID, not a relationship term ID.
  • Use r inside the value to specify relationship types.
  • rt and rf follow the direction in which a relationship was stored; use related to find it from either end.
  • Fulltext search follows MySQL/MariaDB fulltext indexing rules and is not equivalent to substring matching.
  • Very deep linked paths may use the batched compatibility executor rather than one nested SQL expression.
  • Viewport coordinates do not add new query syntax: they are the structured value of the existing geo predicate.
